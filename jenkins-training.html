What is CI/CD?

The Problem Without CI/CD

Imagine 5 developers working on the same codebase. Each writes code for a week, then they try to merge. Conflicts everywhere. Tests fail. Nobody knows whose code broke what. This is called integration hell.

CI/CD solves this by automating the entire process of integrating, testing, and deploying code every time a change is pushed.

CI — Continuous Integration

What it does: Every time code is pushed to GitHub, automatically:

  • Pull the latest code
  • Build the application
  • Run all tests
  • Report Pass or Fail immediately

Goal: Catch bugs early — within minutes of pushing, not days later.

CD — Continuous Delivery/Deployment

What it does: After CI passes, automatically:

  • Package the application
  • Deploy to staging or production
  • Run smoke tests
  • Notify the team

Goal: Ship code to users faster with less manual effort.

The Full CI/CD Flow

Developer pushes code to GitHub │ ▼ ┌───────────────────────────────────────┐ │ CI (Continuous Integration) │ │ │ │ Checkout → Build → Test │ │ │ │ │ PASS ──┤── FAIL │ │ │ │ │ └──────────────────┼──────┼─────────────┘ │ │ │ └──► Notify developer (Red Build) ▼ ┌───────────────────────────────────────┐ │ CD (Continuous Delivery) │ │ │ │ Deploy to Staging → Test → Deploy │ │ to Production │ └───────────────────────────────────────┘ │ ▼ Users get the update
Key insight: In this lab we focus on CI — automated build and test. The Deploy stage is a placeholder that represents where CD would happen in a real project.

What is Jenkins?

Jenkins — The CI/CD Engine

Jenkins is an open-source automation server. It watches your Git repository and automatically runs your pipeline whenever code changes are pushed.

Think of Jenkins as a robot developer that never sleeps — it pulls your code, runs your tests, and tells you immediately if something broke.

Without Jenkins: With Jenkins: ────────────── ───────────── Developer pushes code Developer pushes code │ │ ▼ ▼ Someone manually runs tests Jenkins detects the push │ │ Takes hours / forgotten Runs tests in seconds │ │ Bug found days later Bug found immediately

Core Concepts

Job / Project

A configured task in Jenkins. You define WHAT to do (pull from GitHub, run tests). Jenkins does it when triggered.

Two types: Freestyle, Pipeline
Build

One execution of a job. Each time Jenkins runs your pipeline = one build. Builds are numbered #1, #2, #3...

Green = SUCCESS Red = FAILURE
Pipeline

A sequence of stages that run in order. Defined in a Jenkinsfile. If any stage fails, subsequent stages are skipped.

Checkout → Build → Test → Deploy
Stage

A named section of the pipeline. Each stage has a clear purpose. Jenkins shows each stage's status separately in the UI.

Named sections
Agent

The machine that runs the pipeline. agent any means "use any available machine." In production, you'd have dedicated build servers.

agent any
Jenkinsfile

A text file checked into your repo that defines the entire pipeline as code. Jenkins reads it to know what to do.

Files Explained

The lab uses three files. Each has a distinct role in the CI pipeline.

Jenkins/ ├── calculator.py ← the application (what we're testing) ├── test_calculator.py ← the tests (what Jenkins runs) └── Jenkinsfile ← the pipeline definition (what Jenkins follows)

1. calculator.py — The Application

This is the Python application being tested. It contains four functions — add, subtract, multiply, divide. In a real project, this would be your entire web app or service.

calculator.py
def add(a, b): return a + b # correct version def subtract(a, b): return a - b def multiply(a, b): return a * b def divide(a, b): if b == 0: return None # avoid division by zero return a / b
Why this file matters in CI: When a developer accidentally changes return a + b to return a - b, the tests catch it immediately on the next push. Without CI, this bug might reach production.

2. test_calculator.py — The Tests

This file contains assertions — statements that verify the functions produce correct output. Jenkins runs this file in the Test stage. If any assertion fails, the build turns red.

test_calculator.py
import calculator # import the application module # assert <condition> — fails with AssertionError if condition is False assert calculator.add(2, 3) == 5 # 2+3 must equal 5 assert calculator.subtract(5, 3) == 2 # 5-3 must equal 2 assert calculator.multiply(2, 3) == 6 # 2×3 must equal 6 assert calculator.divide(6, 3) == 2 # 6÷3 must equal 2 print("All tests passed") # only prints if all assertions pass
TestInputExpectedWhat it catches
add(2,3)==52, 35add function returning wrong result
subtract(5,3)==25, 32subtraction logic error
multiply(2,3)==62, 36multiplication logic error
divide(6,3)==26, 32division logic error

3. Jenkinsfile — The Pipeline Definition

This file tells Jenkins exactly what to do when code is pushed. It lives in your repo so the pipeline is versioned alongside your code — this is called Pipeline as Code.

Jenkinsfile
pipeline { agent any // run on any available Jenkins agent stages { stage('Checkout') { steps { git branch: 'main', url: 'https://github.com/YOUR/repo.git' } // pull latest code from GitHub } stage('Build') { steps { sh 'echo "Build stage running"' sh 'python3 --version' // verify environment } } stage('Test') { steps { sh 'python3 test_calculator.py' // run tests } // FAIL here = Red build, Deploy skipped } stage('Deploy') { steps { sh 'echo "Deploy stage placeholder"' } // only runs if Test passes } } }
InstructionMeaning
pipeline {}The entire pipeline definition
agent anyRun on any available Jenkins machine
stages {}Container for all stages
stage('Name') {}A named step in the pipeline
steps {}Commands to run inside a stage
sh '...'Run a shell command
git branch: 'main', url: '...'Pull code from GitHub
Why keep Jenkinsfile in the repo? If the pipeline config is only in Jenkins UI, and Jenkins server crashes, you lose all your pipeline config. With Jenkinsfile in the repo, you can recreate the pipeline in minutes on a new Jenkins server.

Task 1 — Freestyle Job

A Freestyle job is Jenkins' simplest job type. You configure it entirely through the UI — no Jenkinsfile needed. Good for understanding Jenkins basics before moving to Pipelines.

1

Create a new Freestyle job

  • Open http://localhost:8080
  • Click New Item
  • Enter name: calculator-freestyle
  • Select Freestyle project
  • Click OK
2

Configure Source Code Management

  • Select Git under Source Code Management
  • Repository URL: https://github.com/YOUR_USERNAME/Jenkins.git
  • Branch Specifier: */main
3

Add Build Steps

  • Scroll to Build Steps
  • Click Add build step → Execute shell
  • Enter the following commands:
echo "Listing files"
ls
echo "Python version"
python3 --version
  • Click Save
    • 4

    Trigger the build

    • Click Build Now
    • Click the build number (#1) that appears
    • Click Console Output
    • Verify: Finished: SUCCESS

    Task 3 — Automated Triggers: Red and Green Builds

    This is the most important demo — showing how CI automatically catches bugs.

    1

    Enable SCM Polling

    • Go to calculator-pipeline → Configure → Triggers
    • Check Poll SCM
    • Schedule: * * * * * (check every minute)
    • Click Save
    Cron format: * * * * * = every minute. Format is: minute hour day month weekday
    2

    Introduce a bug — trigger a Red Build

    Edit calculator.py and introduce a bug in the add function:

    def add(a, b):
    return a - b    # BUG: should be a + b
    git add calculator.py
git commit -m "Added fault code"
git push origin main

    Wait up to 1 minute. Jenkins detects the push, runs the pipeline automatically.

    Expected result: Test stage FAILS — AssertionError because add(2,3) returns -1 not 5. Deploy stage is skipped. Build status = FAILURE (Red).
    3

    Fix the bug — trigger a Green Build

    Fix calculator.py:

    def add(a, b):
    return a + b    # FIXED
    git add calculator.py
git commit -m "Fixed add function"
git push origin main

    Wait up to 1 minute. Jenkins detects the fix and re-runs the pipeline.

    Expected result: All stages pass. Test stage prints "All tests passed". Deploy stage runs. Build status = SUCCESS (Green).

    The CI Feedback Loop

    Developer pushes buggy code │ ▼ Jenkins detects change (SCM polling) │ ▼ Checkout ✓ → Build ✓ → Test ✗ ← AssertionError caught here │ └──► Build = RED (Deploy skipped) │ Developer notified immediately │ Developer fixes bug and pushes │ ▼ Checkout ✓ → Build ✓ → Test ✓ → Deploy ✓ │ Build = GREEN ✓

    Troubleshooting

    ErrorCauseFix
    python3: not found Jenkins can't find Python Install Python on the Jenkins machine. If using Docker Jenkins, run docker exec --user root jenkins apt-get install -y python3
    No module named 'calculator' calculator.py not in workspace or filename has typo/space Check exact filename with ls -la. Rename if needed: git mv ' calculator.py' calculator.py
    couldn't find remote ref refs/heads/master Branch set to master but repo uses main In Configure, change Branch Specifier to */main
    Build doesn't auto-trigger SCM polling not enabled or schedule wrong Go to Configure → Triggers → Poll SCM → set * * * * *
    Port 8080 already in use Another service using port 8080 Stop the other service or change Jenkins port in ~/.jenkins/jenkins.xml

    What You Just Did — The Big Picture

    You wrote a Jenkinsfile → defined pipeline as code │ ▼ Pushed to GitHub → code + pipeline config in one place │ ▼ Jenkins pulled the code → ran Checkout → Build → Test → Deploy │ ▼ Introduced a bug → Jenkins caught it automatically (Red build) │ ▼ Fixed the bug → Jenkins confirmed the fix (Green build) This is EXACTLY how CI/CD works in real software teams. Every company using DevOps practices does exactly this.
    Key Takeaways for Freshers
    • CI = auto test on every push. Catch bugs in minutes, not days.
    • CD = auto deploy after tests pass. Ship faster, with confidence.
    • Jenkins is the engine — it watches, runs, and reports.
    • Jenkinsfile lives in your repo — pipeline is code, not clicks.
    • Red build = someone broke something. Fix it before it reaches production.
    • Green build = safe to deploy.
    • The test file is just as important as the application — without tests, CI has nothing to verify.
